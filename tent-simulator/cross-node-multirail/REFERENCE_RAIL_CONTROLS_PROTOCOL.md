# RC：原算法的单／双 Rail 同输入对照（2026-10-08）

PV 观测门槛失败后新注册的独立实验。PV 正式 36 组已停止，不覆盖或替换其结果。RC 使用既有 O 观测库，完全不加载新增 provider/PD 计时库；也不声称既有 O 库完全无观测开销。

- 原算法、CPU 内存、1MiB、16×64KiB Slice、总 Q128、1 caller、双方默认 6 lanes、发送端 CPU/内存 NUMA0。
- D0（双 Rail）、S0（仅 erdma_0）、S1（仅 erdma_1），相同 225／675 rps，各 3 次，共 18 次；每次 60s 测量+5s 预热。沿用 PV 预注册随机排列中 reference 子序列，实际顺序写入 plan.json。
- 相比 PV 的 30s，延长为 60s，并将 P99 窗改成 3s，让 225rps 下每窗也有约 675 个请求，且 60s 可提供 20 个完整窗口。此决定在 RC 发流之前固定，对所有 Rail、负载与重复一致生效；不与旧 1s 窗的 P99 CV 混比。
- 报告每次及组中位数/最小最大值：planned→finished P99、goodput、250ms 吞吐 CV、3s P99 CV（每窗≥500请求、≥20个有效窗），所有失败/挂起/最终槽数据验证。D0 附正常选路权重与分片份额的 P95−P05、5pp 确认阈值的往返次数；按既有规则只分析测量第10至60秒。单 Rail 权重震荡为不适用。
- 单 Rail 消除了跨 Rail 分配反馈，但也改变了设备与队列资源；因此“单 Rail 仍有长尾”只能反驳“所有长尾必须由双 Rail 权重震荡引起”，不能证明震荡对 P99 完全无影响。负载是相同总输入，不是相同利用率；未新增各 Rail 饱和校准，不将单 Rail 高负载变慢直接归因为硬件故障。
- 发送端 RDMA 硬件计数器在每个 run 前后记录；不能把聚合计数器唯一归因某个请求。保留已有 manifest 中双方网络计数器，但没有新增接收端 RDMA 硬件计数器，不以发送端无新增错误排除远端或网络问题。
- 保存所有失败，不自动重试。实测期间不编译、分析或上传源码；18组结束后再离线分析。数据仍全在 Git 外；双方 SSH 最后关闭。

验收是完成匹配输入对照与上述证据边界，不宣称本轮实现了新算法或达到 P99/权重联合优化目标。lane=1 对照需要单独匹配双方资源，留待此对照结论之后设计。
